# Relatório Consolidado de Bug Sweep — Plataforma Harven.AI (Tutor Socrático)

## Sumário Executivo

Senhor, a varredura verificada da plataforma Harven.AI revelou **45 defeitos únicos** (após deduplicação de ~62 achados brutos), concentrados em três eixos críticos: **segurança/autorização** (a falha mais grave e sistêmica — IDOR generalizado, secrets forjáveis e takeover de conta trivial), **integridade do motor de diálogo socrático** (chamadas síncronas bloqueando o event loop, pipeline pedagógico morto, estado de sessão nunca persistido) e **pipeline de podcast/TTS e processamento de arquivos** (podcast inexistente, extração silenciosa de texto falhando, contrato de leitura quebrado). A maioria dos achados de "multi-worker" foi corretamente rebaixada porque o deploy real roda **um único worker uvicorn** — mas vários permanecem CRÍTICOS porque são exploráveis hoje, em produção, por qualquer aluno autenticado. **A camada de autorização da aplicação é a única barreira (não há RLS no schema), e ela está ausente em praticamente toda a superfície de chat-sessions, notificações e gamificação.**

## 🔴 CRITICAL (4)

### 1. **Cliente OpenAI síncrono dentro de handlers async congela o event loop inteiro** — IA-Diálogo
`backend/services/ai_service.py:190-191, 254` (+ chamadas em `routes_ai.py:452-513, 653-715, 728-767`)

**O que está errado:** `AIService.__init__` instancia o cliente **síncrono** `from openai import OpenAI` (não `AsyncOpenAI`), e `_call_openai` faz `self.client.chat.completions.create(**kwargs)` como chamada bloqueante. Todos os métodos públicos (`socratic_dialogue`, `generate_questions`, `edit_response`, `validate_response`, `detect_ai_content`) são `async def` mas são `await`-ados direto em handlers FastAPI sem `run_in_executor`/`asyncio.to_thread`/`AsyncOpenAI`. O mesmo padrão atinge ElevenLabs `convert()` (`tts_generate`), `reprocess_content` e Whisper `transcriptions.create` (`ai_transcribe`). O deploy roda **1 worker uvicorn** (`Dockerfile:12`, sem `--workers`) = 1 event loop.

**Quando se manifesta:** Apenas em modo não-mock (com `OPENAI_API_KEY` real = produção). Qualquer chamada LLM/TTS em voo (5-30s para gpt-4o-mini sob carga).

**Impacto no usuário:** Uma chamada LLM lenta de um aluno trava TODAS as outras requisições no worker — health checks, mensagens de outros alunos, até o login. A plataforma parece travar para todos sempre que um turno do tutor está em andamento. Destrói a concorrência multiusuário.

**Direção de correção:** Trocar para `from openai import AsyncOpenAI` + `await self.client.chat.completions.create(...)`, ou envolver as chamadas síncronas em `await asyncio.to_thread(...)` / `fastapi.concurrency.run_in_threadpool`. Aplicar o mesmo a ElevenLabs e Whisper. (Nota: a varredura tinha 3 achados distintos descrevendo este mesmo defeito — mesclados aqui.)

### 2. **IDOR massivo: qualquer usuário autenticado lê/modifica sessões de chat, transcrições e mensagens de qualquer outro usuário** — Segurança
`backend/routes_ai.py:775-911, 934-965` (`get_chat_session`, `get_session_messages`, `add_session_message`, `get_user_chat_sessions`, `complete_chat_session`, `export_session_moodle`, `create_or_get_chat_session`, organizer/prepare-export)

**O que está errado:** Endpoints que recebem `session_id`/`user_id` por path/body só exigem JWT válido (`get_current_user`) e **nunca filtram por `current_user["id"]`**. O cliente Supabase é único, compartilhado, com `SUPABASE_KEY` estática (que decodifica para `service_role` — bypassa RLS) — e **não há nenhuma política RLS no schema**, então a aplicação é a única barreira e ela está ausente. `create_or_get_chat_session` ainda aceita `body.user_id` arbitrário (`uid = data.user_id or current_user["id"]`).

**Quando se manifesta:** Sempre, em produção, para qualquer aluno logado que conheça/enumere um `session_id` (UUID).

**Impacto no usuário:** Exposição cross-aluno de transcrições socráticas completas, nomes e e-mails (PII em `prepare_export`, linhas 956-962); injeção de mensagens forjadas (role/content/agent_type arbitrários) na sessão de outro aluno; marcar sessão de qualquer um como concluída; spoofing de sessão sob outro `user_id`. Quebra de confidencialidade e integridade de registros educacionais.

**Direção de correção:** Adicionar `.eq("user_id", current_user["id"])` (ou verificar `session.user_id == current_user["id"]`) em toda query de sessão; permitir override TEACHER/ADMIN via `require_role`; ignorar `body.user_id` (sempre usar a identidade autenticada). Longo prazo: RLS com cliente Supabase por-usuário. (Mescla 3 achados sobre o mesmo padrão.)

### 3. **Secret de assinatura JWT default `change-me-in-production` permite forjar tokens** — Segurança
`backend/config.py:15` (+ template em `.env.example:11-15`)

**O que está errado:** `JWT_SECRET_KEY` tem default literal `"change-me-in-production"`, sem guarda de startup. Se a env var estiver ausente — **provável**, dado que o `.env.example` documenta nomes ERRADOS (`SUPABASE_ANON_KEY`/`JWT_SECRET` em vez dos lidos pelo código `SUPABASE_KEY`/`JWT_SECRET_KEY`) — todos os tokens são assinados com secret público conhecido.

**Quando se manifesta:** Em qualquer deploy onde a env var correta não foi setada (incluindo seguir o `.env.example` verbatim). No docker-compose atual o `.env` raiz injeta um secret forte, mas é fail-open por design.

**Impacto no usuário:** Bypass total de autenticação. Atacante forja token para qualquer `user_id` existente. **Precisão técnica:** escalar para ADMIN exige `sub` de um usuário ADMIN real (o role vem do registro do banco via `require_role`, não do claim do token) — mas account takeover de qualquer usuário com id conhecido é trivial.

**Direção de correção:** Falhar no startup se `ENVIRONMENT==production` e `JWT_SECRET_KEY in ('', 'change-me-in-production')` ou < 32 chars. Reconciliar `.env.example` raiz e `backend/.env.example` para usar os nomes reais (`SUPABASE_KEY`, `JWT_SECRET_KEY`). (Mescla config.py + .env.example + db-config-deploy duplicatas.)

### 4. **Token de reset de senha retornado no corpo HTTP (e logado em texto puro)** — Segurança
`backend/main.py:443-446`

**O que está errado:** `request_password_reset` (endpoint não autenticado) gera o token de reset e o **retorna no JSON da resposta** (`return {"message": "...", "token": token}`) E o loga em INFO (`logger.info(f"...: {token}")`). O comentário admite ser "TEMPORARY". Não há gating por ambiente.

**Quando se manifesta:** Sempre — qualquer um que saiba o e-mail da vítima chama `POST /auth/request-reset`, recebe o token na resposta, e chama `POST /auth/reset-password`.

**Impacto no usuário:** Account takeover total trivial e não autenticado, incluindo contas ADMIN. A proteção contra enumeração de e-mail é anulada (o token é entregue ao requisitante). Exposição secundária persistente via logs (Sentry/stdout) dentro da janela de 1h.

**Direção de correção:** NUNCA retornar o token; entregar apenas por e-mail. Remover o token da resposta e dos logs. Persistir tokens hasheados no DB com flag single-use. (Mescla o achado do corpo HTTP com o achado de logging.)

## 🟠 HIGH (14)

### 5. **Pipeline Editor/Tester (quality gate pedagógico) nunca é encadeado ao diálogo ao vivo** — IA-Diálogo
`backend/routes_ai.py:261-292`

**O que está errado:** A arquitetura anuncia pipeline de 6 agentes (Editor refina, Tester valida com APROVADO/NEEDS_REVISION/REJECTED). Mas o diálogo ao vivo (`ChapterReader.tsx → aiApi.socraticDialogue`) só chama `/api/ai/socrates/dialogue`. `/editor/edit` e `/tester/validate` são endpoints isolados nunca invocados no fluxo (wrappers frontend `editResponse`/`validateResponse` não usados). **Nuance honesta:** as regras pedagógicas existem como instruções soft no `SOCRATES_PROMPT` (não revelar resposta, ≤2 parágrafos, terminar com pergunta) — o que falta é o segundo passe determinístico de enforcement/regeneração.

**Quando se manifesta:** Em todo turno do tutor em produção.

**Impacto:** A camada de validação/edição é código morto. Uma resposta socrática degradada ou que vaze a resposta é mostrada ao aluno sem filtro; o veredito do Tester não barra nada.

**Correção:** Encadear server-side dentro de `socratic_dialogue`: Socrates → Editor → Tester, retornando só output APROVADO (regenerar em REJECTED); ou remover o framing multi-agente enganoso.

### 6. **Turnos do tutor (assistant) nunca são persistidos — histórico e export Moodle perdem todas as respostas da IA** — IA-Diálogo / Perda de Dados
`backend/routes_ai.py:219-240`

**O que está errado:** `/api/ai/socrates/dialogue` só gera e retorna a resposta — **nunca escreve em `chat_messages`**. O frontend (`ChapterReader.tsx:395`) chama `addMessage` apenas para a mensagem 'user'; a resposta 'assistant' fica só no estado React local (linhas 403-410). Pior: o `startChat` inteiro (mensagem de abertura do aluno + primeira pergunta socrática) também nunca é persistido.

**Quando se manifesta:** Em todo recarregamento de página; em todo export.

**Impacto:** Ao recarregar, `GET /chat-sessions/{id}/messages` retorna só mensagens do aluno — a metade pedagogicamente valiosa (as perguntas socráticas) some. O export Moodle/xAPI reconstrói uma transcrição incompleta, deturpando a sessão para o LMS/professor.

**Correção:** Persistir ambos os turnos server-side dentro da rota `socratic_dialogue` (inserir a mensagem do aluno + a resposta do assistant com role/agent_type), tornando o backend a fonte única de verdade.

### 7. **`create-or-get-session`: race read-then-insert sem unique constraint → sessões duplicadas → falha 500 permanente** — IA-Diálogo / Concorrência
`backend/routes_ai.py:784-807` (+ `supabase_schema.sql:122-132` sem `UNIQUE(user_id, content_id)`)

**O que está errado:** `SELECT ... maybe_single()` seguido de `INSERT` sem transação nem unicidade DB. Duas requisições concorrentes (duplo-clique, duas abas) inserem ambas → sessões ativas duplicadas. Daí em diante, todo `maybe_single()` sobre esse filtro lança `APIError` (PostgREST retorna múltiplas linhas) → exceção não tratada → HTTP 500.

**Quando se manifesta:** Sob concorrência no mesmo user+content; depois disso, **permanentemente** para aquele par.

**Impacto:** Histórico fragmentado, contagem duplicada em analytics, e o fluxo "retomar tutoria" retorna 500 para sempre naquele par (user, content).

**Correção:** `UNIQUE(user_id, content_id)` em `chat_sessions` + upsert/ON CONFLICT; ou `.order().limit(1)` em vez de `maybe_single()` tratando a violação de unicidade.

### 15. **Achievement unlock colide na primary key — segundo usuário a desbloquear o mesmo achievement recebe 500** — Data Loss
`backend/routes_admin.py:1140-1176`

**O que está errado:** `unlock_achievement` insere row com `id=achievement_id` (id do catálogo) + `user_id`. Mas `user_achievements.id` é a PRIMARY KEY (`supabase_schema.sql:236`). O dedup é por-usuário (`.eq('user_id').eq('id')`), então para o usuário B (sem essa row) prossegue e insere `id=achievement_id` de novo → violação de unicidade → 500.

**Quando se manifesta:** Quando um segundo usuário tenta desbloquear um achievement já desbloqueado por outro.

**Impacto:** Só o primeiro usuário consegue desbloquear um dado achievement; os demais crasham com 500. Achievements são efetivamente globais de uso único.

**Correção:** Gerar UUID fresco para `id`; armazenar a referência de catálogo numa coluna separada (`achievement_key`); dedup em `(user_id, achievement_key)` com unique constraint.

### 20. **LTI launch confia em roles do cliente para atribuir ADMIN e cria usuários com senha previsível** — Segurança
`backend/routes_ai.py:1138-1198`

**O que está errado:** `lti_launch` mapeia o campo LTI `roles` via `ROLE_MAP` que inclui `'administrator' → 'ADMIN'`. ### 53. **Allowlist de content-type é controlada pelo cliente; sem validação de magic-byte** — Processamento de Arquivos / Segurança
`backend/main.py:1205-1206`

**O que está errado:** Todos os endpoints de upload validam `file.content_type` contra `ALLOWED_*_TYPES`, mas o content_type vem verbatim do header multipart (controlado pelo atacante). `save_file` só checa extensão (também controlada).
